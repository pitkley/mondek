# LiveView overview prototype

Open `/next` on a controller built from this checkout. Existing routes remain available through links explicitly marked as existing pages. This is a read-only investigation prototype, alongside the current interface; it does not change monitoring, configuration, acknowledgement or notification behavior.

The overview presents a compact installation summary, results needing attention, healthy results and a contextual detail panel. The detail panel overlays the right side of the board without changing list geometry or scroll position, and fills the viewport width on narrow screens. All row types share hover and selection styling. Selecting the same row again, clicking outside the panel, using its close link or pressing Escape dismisses it; another row switches the selected evidence. Selection is recorded in `/next/results/:id` or `/next/expected/:id`; browser Back, reload, reconnect and closing the panel preserve the search and page parameters. Closing the panel returns focus to the opening link, unless focus has moved into search. Background refreshes update evidence every two seconds without moving focus.

The page uses two coherent surfaces: the overview header with its installation summary, and the results section with its search toolbar, attention/healthy headings, missing-monitoring subsection and pagination footers. Labels, guidance and empty states stay with their owning content instead of floating on the canvas. Summary and desktop tables share the same 45% first-column boundary and 16px content inset; narrow screens stack them with a shared 12px inset.

Focus the shared search field to choose Environment or Target, then type and select a value in the same field. Applied filters and search text appear as removable chips inside the field. Press Enter to submit plain text, or choose **Search for this text** when the text also matches a filter name. The picker offers values from current result streams and resolved declarations, including targets with no selected runner. The shared search text and filters combine across all three lists. Each field accepts one value, and selecting another value replaces it. Applying a filter shows the remaining unused filters. With an empty input, Backspace reopens the last filter chip and selects its current value, or removes the last plain-text chip. Backspace again removes the filter if the value is selected or empty. Escape cancels an edit. At the start of the search input, Left opens the last filter chip for editing. Left and Right move between unchanged chips and back to the search input. Apply or cancel a changed value before moving to another chip. The URL preserves applied chips when opening evidence or sharing the overview. The installation summary remains installation-wide.

## Actual Mondek data

Each observed row is one native result stream, owned by its observing runner. Target/check, monitored environment, source and runner identify the row; health, original measurement age, freshness and the check-authored summary belong to that stream alone. Selecting it shows only its findings, configuration link and incident actions. Matching source/check/result/environment/target scopes do not establish equal code, effective settings or datasource access, and never produce a consensus verdict.

When other active results declare the exact same scope, a collapsed **Related results for this scope** disclosure offers links to their independent evidence. Missing historical identities stay independent. This is an optional investigation aid, not the ordinary overview structure. Each failing or stale stream remains independently visible in the board. Runner replacement overlap and independent collection loss remain acceptance scenarios, rather than the primary design example.

The overview counts observations separately from declared result scopes. Last measured health includes retained evidence, while freshness comes from the existing inspection classification. Declared coverage additionally requires current desired-version evidence according to the existing Coverage context. No selected runner is a distinct declaration state, not a fabricated measured result. Older or unconfirmed catalogues and unresolved declarations remain accessible through a review link; zero active results alone does not establish a new installation.

Each observed section pages thirty result streams, with complete matching totals. Related-stream inspection is bounded to the selected result and up to 24 active peers (a retired selected result may accompany 25 active peers). Unobserved declarations use Coverage's existing 25-row pagination and bounded observer inspection. The gap section is hidden when the installation has no gaps and shows an empty state when filters exclude all existing gaps. Results and monitoring gaps have separate counts. Each section has its own page parameter. Search applies before paging and includes runner names; the installation summary remains installation-wide. Lists describe results rather than incident episodes, and acknowledged health failures remain visible.

The overlay uses nonmodal desktop behavior and modal narrow-screen behavior, with background controls inert and keyboard focus contained while it covers the viewport. Its close control stays reachable while scrolling. Disconnection warnings appear within the panel as well as on the board; frozen evidence never silently implies a live connection. Declaration investigation links preserve the preview's selected item and filters.

## Component foundation

The prototype uses pinned `@patternfly/patternfly` 6.7.0 HTML/CSS components: navigation, tables, labels, badges, titles, buttons, form controls and cards, with upstream design tokens. It uses platform fonts and omits optional font/icon assets. Mondek owns the page composition, compact responsive observation rows, nonmodal overlay placement and small LiveView focus/keyboard hook. React is not included. PatternFly selection for this prototype is not a permanent system decision.

`PreviewLayouts` loads only `preview.css` and `preview.js`; existing pages continue loading their own assets. Keep the bundles independent when adjusting density or styles. PatternFly's npm archive omits its license file, so the existing license collector retains a version-scoped upstream notice from the package's published source commit. Generated credits include the dependency.

The overview uses Pearl surfaces, blue result links and a compact sidebar.

Desktop result rows place identity/context and state/age/summary on one scan line. Long text truncates visually with full values in accessible link text, hover titles and the selected evidence panel; narrower layouts wrap instead. Header, summary and toolbar padding is reduced. Table headers have a lightly tinted band and boundary rules; alternating body rows provide scan lines without using status colors. The Results section owns the shared search bar and all three lists. Needs attention, declared results without a selected runner, and current healthy results use matching level-three headings and counts for their own list. Each heading, table and pager is enclosed in its own inset bordered group, with a small gap between groups. The enclosure attaches each heading to the following table rather than leaving it between two full-width tables. Summary columns share the groups’ horizontal inset and column boundary. Body rows retain compact padding, with hover and selection overriding striping. Thirty-result pages remain bounded, with independent pagination for attention and healthy lists.

The sidebar uses a filled blue selection and stronger text, an independent hover treatment, and thin separators between destinations. List padding is reset explicitly so icons and labels share the available width. Decorative icons reuse Mondek's existing credited Lucide sprite; labels and `aria-current` remain the accessible navigation identity. Existing-page links still lead to the current interface.

## Light palette comparison

The masthead's **Theme** menu switches between **Pearl** (near-white neutral canvas with white surfaces), **Clear** (white canvas and blue accents), **Mist** (cool blue canvas with white surfaces), **Linen** (warm off-white and teal accents), and **Original** (the previous PatternFly gray palette). Pearl is the initial choice: its `#f6f7f8` canvas separates white surfaces while reducing the blue tint of Mist (`#f2f7fc`). Existing saved choices remain selected. The preference is stored only in this browser under `mondek-preview-theme`; changing it preserves the current URL, selected evidence, layout, spacing and status meanings. Storage-disabled browsers can still switch for the current page. Legacy pages keep their own styling.

These are Mondek-authored values mapped to existing PatternFly semantic tokens; no additional theme package, font, icon or third-party palette is imported. Existing PatternFly attribution remains in the generated credits. Prior-art guidance informed the separation of background/surface/selection roles: [Carbon's white/light layering model](https://www.carbondesignsystem.com/building-blocks/foundations/color/overview) and [USWDS role-based theme colors](https://designsystem.digital.gov/design-tokens/color/overview/). They are research references, not copied implementation assets.

Browser checks compare list and overlay geometry between themes, retain selection and preference through reload, and scan each palette for accessibility at desktop and 320px widths.

## Incident investigation

Open `/next/incidents` to see health failures and monitoring loss in one list. The default view shows open incidents and includes a bounded first page of each type. Choose one type to page through its full history. Each row represents one incident episode, including a single row for a shared health incident. The shared chip search starts with Status: Open. Edit the chip to browse closed incidents or remove it to show all statuses. Use the Type chip to narrow the list or enter text to search incident names and scope. Type, search text, status and page are stored in the URL.

Health details show recorded failure evidence and link separately to the current result. Monitoring loss shows the affected results and why measurements are missing, with links to current result evidence or expected monitoring. Evidence links return to the incident and preserve its list filters. Acknowledgement, delivery controls and full incident history remain available through the explicitly labelled existing incident page.

The monitoring-loss browser suite walks the mixed list, type filter, both incident details and the round trip through live result evidence using real runner data. Configuration, maintenance, runner administration, notification delivery and full inventory remain on their existing pages. A broader replacement needs its own page and action coverage review before cutover.
