# Operating the local slice

## What is running

`mondek demo` starts four Compose services: PostgreSQL, the Phoenix controller/UI, the Python runner and a controllable local target/receiver. The runner owns a three-second fixed schedule, with a two-second execution limit per assignment and twelve-second source validity. Filesystem capacity is `shutil.disk_usage`'s used/total percentage in the Linux container; it is not macOS host capacity, inode monitoring or an expected-mount inventory. The HTTP assignment probes `/ready`; the ordinary Python consumer reads backlog from `/data` through a bounded datasource.

The local fixture forwards the runner's control and ingestion requests to the controller. This supports a real lost-ingestion-reply test: it commits at the controller, closes the HTTP connection, and records the retry's durable duplicate disposition. In normal mode it forwards responses directly. Control long polls, uploads, check subprocesses and the browser use separate requests/execution paths.

## Operator flow

Overview shows aggregate coverage and a prioritized list of results needing attention. Open Checks to browse the full result inventory, with last measured health, measurement freshness and source age. Heartbeats do not count as coverage. Starting another run retains the previous verdict without making it newer. A missing result, worker crash or timeout leaves coverage unavailable; an expired source marks health stale. Neither state closes an incident. The confirmed measurement keeps its own observation and configuration identity when a later failed execution uses newer configuration.

Checks and targets are declared in installed consumer code and published by each runner. The admission limit is 512 scheduled checks per runner and 16 expected results per check. The UI lists results and scheduled checks separately, with bounded pages and search. A check may delegate its complete typed parameter set; otherwise configuration remains read-only. `target:8080` names the local fixture, `host.docker.internal` reaches a service on this computer, and loopback refers to the runner itself. Filesystem thresholds use CRIT-first `>=` comparison with `0 ≤ warning < critical ≤ 100`. Saving carries the reviewed revision; conflicting saves preserve the draft and require explicit review of current values before trying again. Saved, Prepared, Active and Measured stages are persisted. An offline save waits for the runner; retained health keeps its original policy. New limits collect fresh input, and closure under changed policy says configuration changed.

Fresh WARN/CRIT opens one incident per independently tracked result; fresh OK under the same policy closes it as measured recovery. Siblings from one execution can have different health and separate incidents. Incident detail links original evidence and notification attempts. [Acknowledgement](ACKNOWLEDGEMENTS.md) applies to one incident using the fixed local operator: until the incident ends by default, or for a chosen duration/UTC expiry. It ends on escalation above the captured severity ceiling. [Scheduled maintenance](MAINTENANCE.md) covers selected scheduled checks or exact stable targets within their source and monitored environment, with explicit start, end and timezone. [Weekly series](RECURRING-MAINTENANCE.md) save a finite set of those windows; future dates do not imply a hold between windows. Both controls preserve health/history and the runner's schedule. Ending one gate does not end the others.

Publish a complete inventory without a check or output to withdraw that monitoring. The controller excludes the removed result from expected coverage, closes its incident with a source-removal reason and supersedes future delivery work without claiming measured recovery. Late reports retain their identity as historical evidence. Unchanged siblings keep their incidents and configuration. Reintroducing a withdrawn output creates a new monitored incarnation; old target/history links remain intact. Failed discovery retains the last complete inventory. A source deployment is local to its runner; the controller does not import code or decide which files or databases it may access.

For a whole installation/source publication, **Coverage → Publishing runners** provides reviewed retirement, replacement and restoration, including when an observer is unavailable. Retirement fences automatic re-entry; replacement requires compatible fresh evidence from the named successor. Shared incidents continue only through their independently admitted contributors. Restoration requires successful new discovery and new membership identities. See [observer lifecycle](OBSERVER-LIFECYCLE.md) for the authority and evidence boundaries.

The overview and compatibility snapshot APIs report `assignment_limits.active` across the installation. Their `active_limit` is scoped by `active_limit_scope: "per_runner"`; a global total above 512 is valid when multiple runners each remain within their own limit. The compatibility snapshot returns at most 100 active assignment details, independently of that total.

## Local failure controls

Run these inside `devenv shell`. The receiver never relays to an external recipient.

```sh
curl -sS -H 'Content-Type: application/json' -d '{"ready":false}' http://localhost:58080/mode
curl -sS -H 'Content-Type: application/json' -d '{"ready":true}' http://localhost:58080/mode
curl -sS -H 'Content-Type: application/json' -d '{"webhook":"reject"}' http://localhost:58080/mode
curl -sS -H 'Content-Type: application/json' -d '{"webhook":"ok"}' http://localhost:58080/mode
docker compose exec runner python -m mondek_runner --status
```

Additional fixture modes are `data_mode` (`ok`, `slow`, `crash`, `oversize`), `webhook` (`ok`, `reject`, `drop`, `slow`) and `ingest_reply` (`ok`, `drop_once`). Modes persist across fixture restart. `/records` returns recent durable receiver receipts and `/transport-records` returns bounded ingestion forwarding/reply records. These are explicitly local testing facilities.

The demo's Python policy class combines queued-count thresholds with the application's reported processing state. Setting `{"backlog":6,"processing_enabled":false}` through `/mode` produces a warning finding for count and a critical finding for queued work with processing disabled. The result detail page shows both findings and their original confirmed measurement. Restore with `{"backlog":2,"processing_enabled":true,"data_mode":"ok"}`. This policy is ordinary consumer code, with no special controller interpretation. Its empty paused queue is acceptable unless an authored count threshold itself warns.

Result details are optional escaped plain text, capped at 16 KiB each and included within the existing aggregate output/spool limits. Result inspection labels confirmed measurement details separately from latest execution details; unavailable collection retains the old confirmed context without refreshing it. Individual run cards preserve their original result details. Full details are not included in notification payloads.

`secondary_ready` independently controls `/ready-secondary` and the second Prometheus fixture series. Change it with the same `/mode` endpoint using `{"secondary_ready":false}` or `true`; the primary service remains independent. The parity fixture also supports UUID-scoped transport outages and a selected runner's one-shot dropped ingestion reply; these are used only in isolated acceptance projects.

## Delivery and storage bounds

Webhook occurrences have immutable IDs, payloads and destinations. Oban owns durable due/retry work, and attempt start commits before contact. A receiver accepting a request before the reply is lost can receive the same occurrence more than once. The UI distinguishes attempted, accepted and ambiguous/failed delivery; acceptance does not mean a human read it. Recovery supersedes obsolete firing work while preserving history.

Notification jobs have a one-minute execution limit, including database work; the supported SMTP request deadline is at most thirty seconds. Orphan recovery waits two minutes and checks once per minute, so interrupted executing work can take up to about three minutes to become available again. A late failed attempt retains its own outcome without erasing an already accepted delivery or its acceptance time.

After the bounded automatic budget is exhausted, repairing the receiver alone does not restart work. Retry notification records a reason and transactionally queues another budget for the same still-relevant occurrence. Earlier attempts remain visible. A concurrent retry cannot schedule a second live job. Retired, obsolete, delivered or still-running work cannot be retried. Failure notification gates remain effective; closure notifications bypass those gates as before. The normal budget is 100, configurable for local testing with `MONDEK_NOTIFICATION_MAX_ATTEMPTS` (1–100); browser fixtures use three to exercise real exhaustion promptly.

The runner defaults to three concurrent check subprocesses, one per assignment, with oldest-due scheduling. Preparation uses one additional subprocess. Independent control and upload each use one short-lived HTTP helper, with total deadlines of eight and five seconds; expiry kills and reaps the helper. Consumer discovery has a fifteen-second supervisor deadline and one small independent watchdog in its owned process group. The watchdog terminates that group on supervisor/helper loss or its sixteen-second fallback deadline, including ordinary descendants; it does not depend on consumer Python remaining responsive. This is lifecycle cleanup, not a sandbox for code that deliberately escapes its process group. Capture is capped at 64 KiB combined output per check, results at 16 and summaries/diagnostics at 2048 UTF-8 bytes. Consumers must bound their own datasource reads; the examples do so. Ordinary HTTP requests cap at 256 KiB with 32 observations per batch; complete inventory requests and control responses allow 4 MiB. The Compose spool caps at 512 reports or 2 MiB and evicts oldest evidence with a persisted loss counter. Reconnection uploads original IDs/times; it cannot certify continuity through a reported gap. Restart preserves installation identity, increments boot/session authority and skips obsolete missed intervals. Limits bound resource use; throughput must be measured under the deployment's actual CPU and collection cost.

Checks, configuration and incidents use searchable pages of 50 rows, capped at 100, with totals independent of the current page. Environment filters use stable IDs; labels can change without merging different environments. Runner inspection lists up to 100 installations. Its scheduler panel reports worker occupancy, checks waiting for execution and the oldest due delay separately from buffered reports waiting for upload. Those are the last heartbeat's values, not a live countdown or a substitute for measurement freshness. Preparation and activation backlogs remain distinct.

Configuration's adoption filter finds currently desired versions at Saved, Prepared, Active or Measured after leaving the original edit. It persists in the URL and distinguishes matching, pre-filter and installation-wide counts. Measured is a milestone; the corresponding evidence can later become stale or unavailable. Failed collection does not undo that milestone or make the last measurement fresh.

The compatibility snapshot includes open incidents, the 100 most recently closed episodes, the oldest 100 unresolved occurrences and 100 terminal occurrences. Its unresolved totals and omission count are exact. Runners & delivery pages through all retained occurrences, 25 at a time, with a status filter and separate filtered/global totals; it initially shows outstanding work. Exhausted notifications remain outstanding until obsolete. The page includes at most 100 recent attempts belonging to its displayed notifications, with an explicit omission count. Selecting a result or incident loads its own bounded evidence, delivery and control history with totals and omission counts, so unrelated recent activity cannot make its delivered firing or attempts appear absent. Original shared report payloads remain intact while the selected result's evidence is identified separately.

The controller keeps ordinary exact replay receipts for up to seven days or 100,000 reports, while protecting current and unresolved references and preserving per-assignment sequence progress after pruning. Protected references can exceed the ordinary receipt cap. Terminal incident/delivery/control history expires after thirty days; referenced configurations and the latest twenty per assignment remain protected. Docker service logs cap at three 10 MiB files per service. This small slice does not claim fleet capacity, off-host backup, disaster restore or unattended availability. Normal restart with its existing volumes is the supported recovery case.

Retired check identities, reasons and compact last-state projections remain retained. Their last raw execution/confirmed evidence stays protected for thirty days after retirement, then ordinary receipt retention applies unless another retained reference protects it. The UI discloses missing raw evidence. Retired configuration authority no longer pins old versions beyond the normal latest-twenty/reference rules. Paged inventory membership filters include withdrawn results and checks; direct result and incident pages preserve the selected incarnation's history. These bounds limit work and inspection size; permanent compact identities mean this is not a fixed total-storage guarantee under unlimited churn.

Publication lifecycle decisions retain their exact successor measurement references and original configurations beyond ordinary receipt retention. These reports are directly inspectable from the saved decision. Unrelated observations retain their normal lifetime; lifecycle history currently has no automatic expiry, so repeated decisions also contribute to retained storage.
