# Stable check maintenance design

A stable check selector matches the exact source ID, source check key and result environment, with an optional exact target kind and key. A missing environment matches only the absence of an environment. Without a target the selector includes every output of that check in the selected environment. With a target it includes every output of that check declaring that target. A check key rename requires a new reviewed selection. Application and cancellation continue to use the existing source and maintenance locks.

Store the new selector as an entry in a composite window, including a `source_key` field only for this scope. Existing check and target entries retain their serialized shape. A forward migration extends the database validation constraint and matching function. No maintenance window rows need to be rewritten. The chooser offers both stable scope variants and discovers their identities from active results. Preview requires an existing match to create a new selector. Saved windows can be inspected, edited and canceled when all current matches are gone.

Use the same identity for preview, notification eligibility, delivery wakeups, condition inspection and history protection. Keep the existing condition rule that maintenance must cover every active supporter of a fact to hold that fact. Keep the monitoring-loss rule that every current gap in the episode must be covered. Use a runner gap's admitted assignment and a declaration gap's exact coverage identity, including when a declaration has no selected runner. Store the check key with the gap details for history. Backfill existing gaps where their assignment or accepted coverage declaration still establishes the key.

Verify exact matching across replacement, zero admitted results, and similar keys in other scopes. Exercise grouped delivery with mixed supporters and unassigned declared coverage. Verify editor and saved detail behavior through their normal browser routes.
