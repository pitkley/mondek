# Runner state without a persistent volume

A pod-local state directory is the first option to qualify for read-only monitoring that tolerates a new observer and loss of unuploaded evidence when a Pod is replaced. Mount a disk-backed Kubernetes `emptyDir` at `MONDEK_STATE_DIR`. This keeps the current runner and its local SQLite journal. Keep a dedicated durable directory for deployments that require continuity across Pod replacement. A persistent-volume-free deployment still needs writable local state while it runs. [Kubernetes volume lifetimes](https://kubernetes.io/docs/concepts/storage/volumes/#emptydir)

## What the runner stores

| State | Why it matters when storage disappears |
| --- | --- |
| Installation ID, boot counter and session | The directory owns the installation ID and boot counter. Each start advances the boot and creates a session. A fresh directory creates a new installation at boot 1. A source name, Pod name, target ID and installation ID identify different things. |
| Accepted inventory and assignments | Inventory revision and locally adopted assignment definitions support reconnect and compatible offline collection. Saved controller configuration stays with its assignment. A fresh installation needs to publish, prepare and adopt its own assignments before it can collect on the controller's behalf. |
| Verified source snapshots | Snapshots retain consumer source and declared private construction inputs. They do not pin a separately changed installed dependency environment. The runner verifies saved revisions before executing them offline. |
| Execution journal and spool | Allocation commits a report UUID, sequence, assignment, session and generation before launching a worker. Restart against retained state converts unfinished allocations into incomplete reports. Completed reports keep their original evidence and timestamps until acknowledged or evicted by the bounded spool. Loss of the directory can erase both unfinished allocations and all unuploaded reports. |
| Optional consumer-state read cache | The cache starts empty in every runner session, even when the directory is retained. During one session, eligible stale reads retain the original update time and expiry. Confirmed misses and mutations can invalidate a cached address. A replacement retains neither cache eligibility nor assignment-local state identity. Source-wide consumer state remains on the controller and can be read online by newly admitted assignments. |

The [runner journal](../runner/mondek_runner/state.py), [runtime](../runner/mondek_runner/runtime.py), [runner protocol](../contracts/v1/protocol.md) and [consumer-state read policy](CONSUMER-STATE.md#opt-in-to-a-stale-read) define these boundaries. Any storage option must preserve report identities and original acquisition times when replaying retained evidence.

## Storage options

| Option | Restart and replacement | Outage and overlapping starts |
| --- | --- | --- |
| Local ephemeral directory | A retained `emptyDir` across container restarts in the same Pod preserves identity, snapshot and queued evidence. Pod deletion, eviction or replacement drops the volume. A new directory starts a new observer. | An already prepared runner can keep collecting and buffering through disconnection as long as its directory survives. A fresh replacement needs the controller before it can adopt assignments. The local lock prevents overlapping starts on one directory. Separate Pods can collect simultaneously as independent observers. |
| Dedicated durable directory or attached volume | Reattaching the entire state directory to one replacement preserves the same installation, saved assignment state and bounded replay. This requires the matching installed environment and ownership of the same storage. | A compatible runner can resume offline when the volume is available. Stop the predecessor or verify storage fencing before exclusive attachment. SQLite WAL requires a local filesystem with supported locking and shared-memory semantics. A network fileshare mounted by multiple hosts is unsuitable for the current journal. |
| Controller-backed identity and state | A future controller claim could preserve logical installation identity across storage loss. A successor would still need to prepare locally, and locally buffered reports would still be lost unless they were uploaded to durable storage before the loss. | A cold or replacement runner cannot claim ownership during a controller outage. An execution lease can restrict cooperative new launches and fence admitted writes. An isolated predecessor can continue executing code until its locally enforced lease limit or an external fence takes effect. A controller-hosted spool also becomes unavailable when the controller is unavailable. |
| External transactional state or asynchronous checkpoints | A strongly consistent store could retain a journal and spool across nodes if it owns allocation, queue transitions, acknowledgements and a monotonically fenced writer lease. Snapshot objects could be stored separately with verified digests and explicit private-input handling. Asynchronous copies only recover through the last durable checkpoint. | A remote-only journal cannot durably allocate or finish reports while the store is unreachable. A local buffer can let an already admitted runner continue, with acknowledged loss of unreplicated work if its Pod disappears. A backend needs proven stale-writer exclusion and idempotent operations, including when the client loses a committed reply. |

An exclusively attached block volume can preserve the existing state model if its filesystem and attachment semantics are qualified. A Pod restart is often shorthand for two different events. Treat a container restart in one Pod and a replacement Pod as separate operations, even if the latter lands on the same node with the same name. [Kubernetes volume lifetimes](https://kubernetes.io/docs/concepts/storage/volumes/) · [SQLite WAL constraints](https://www.sqlite.org/wal.html#overview)

## Identity and fencing

The current controller rejects an older boot or a different session at the same boot for one installation. Its observation endpoint verifies the transport session, then decides whether each report can become current using the report's original session, authorized generation, active assignment and sequence. A restarted installation can upload surviving reports in its new transport session. Previously committed reports replay with their original disposition, and new admissible reports from an old session are historical. A replacement with a new installation ID owns a separate publication. Matching targets and source names do not transfer incidents, instance exceptions, stream identities or retry budgets. An operator can review the successor's coverage and retire the predecessor through the [existing publication lifecycle](OBSERVER-LIFECYCLE.md#reviewed-lifecycle).

For a future identity-preserving replacement mode, authenticate a workload principal and bind it to an operator-assigned installation slot. Give each acquisition a controller-issued, monotonically advancing epoch and session. Use an idempotent acquisition request so a lost reply cannot create a second grant. Verify the admitted epoch inside the same transactions as control, inventory, observation admission and consumer-state writes. Allocate report sequences durably, or explicitly migrate ordering to an epoch plus sequence while retaining older exact replay. Pod names and client-selected boot counters cannot substitute for that boundary. The current machine gateway protects runner routes but does not bind a credential to a Mondek installation slot. [Controller authentication](CONTROLLER-AUTH.md)

Admission fencing prevents stale activity from becoming current at the controller. It cannot interrupt disconnected Python or undo external side effects. Any future single-executor promise must define when new execution stops during a partition and how the downstream system fences writes made by still-running workers. Keep independent ephemeral observers limited to read-only checks, including during a rolling overlap. Uncommitted work lost with a Pod is a measurement gap. Existing monitoring-loss handling and explicit retirement remain the mechanisms for making that gap visible.

## Recommended qualification

Qualify a disk-backed `emptyDir` with an explicit size limit and one runner per state directory. Use existing settings and the standard exec worker so storage lifetime is the only variable. Document the measured loss boundary before offering this as a deployment recipe. Keep durable deployments as the choice for workloads that require identical observer identity and replay across node replacement. Revisit controller-issued identity only if a consumer needs that identity and can accept online acquisition. Revisit external journals only if preserving unuploaded evidence across node loss is also required.

1. Restart the runner container with the same Pod and retained directory while uploads are denied. Verify the same installation, a new session, unchanged IDs and times for surviving reports, and incomplete evidence from an interrupted execution. Restore connectivity and confirm fresh authorized observations independently of historical replay.
2. Replace the whole Pod while the controller is unavailable. Verify the loss of the unuploaded local queue and the absence of adopted assignments until registration and preparation complete. After recovery, verify distinct installation and stream IDs, retained controller history and reviewable predecessor retirement.
3. Exercise overlap by starting a second process against the same directory, then by starting a second Pod against its own directory. Verify local exclusion and distinct publications respectively. Retire a disconnected predecessor, reconnect it and verify that its buffered work cannot become current or clear the successor's monitoring gap.
4. Repeat a qualifying state-read outage within one session and across restart. Verify expiry and write invalidation, an empty cache at restart and online access to surviving source-wide values after the replacement is admitted. Fill the bounded spool and observe controlled eviction separately from loss of the whole directory.

This study reviewed the published `v0.0.9` state and admission paths. A pinned-Python probe confirmed local lock exclusion, original report IDs and sessions surviving a retained-directory restart, incomplete evidence for an interrupted allocation, and fresh identity with an empty replacement directory. The current real [runner acceptance](../tests/e2e/acceptance.py) covers outage, bounded spool and retained-directory recovery. The Kubernetes replacement cases above are qualification criteria.
