# Runtime incident correlation proposal

Status: design proposal, 2026-11-16. No runtime behavior or public API described here has been implemented. This extends the current [shared-condition contract](GROUPED-INCIDENTS.md) with a separate correlation layer; it deliberately introduces the causal notification inhibition excluded from that increment.

## Recommendation

Keep `Condition` as a declaration of equivalent evidence, with one condition per output. Add runtime correlation between existing health incident episodes, including shared-condition episodes, without changing their evidence ownership or lifetimes. Give the correlated collection its own durable episode, called a **correlation case** in this proposal. A case has an optional anchor incident representing the suspected upstream problem, independently measured member incidents, audited membership and its own operator attention scope.

This supports a cluster network failure with dozens of app incidents underneath one operator incident. It also permits an external model such as Jev to propose the same decisions an operator could make. Mondek owns validation, concurrency, notification eligibility and history; the model supplies a bounded decision, never execution or delivery authority.

Use one primary notification-owning case per member episode initially. Support multiple noninhibiting relationship dimensions alongside it. Arbitrary nested suppression graphs, multiple notification parents and automatic remediation are outside the first implementation.

## Fit with the current implementation

| Existing concept | Preserve | Proposed addition |
| --- | --- | --- |
| `Condition` | Exact namespace/key/environment equivalence; independent contributions and controls | A condition episode can itself be a member of a correlation case |
| `CheckGroup` | One source/environment browsing group; no incident semantics | Explicit attributes or selectors can contribute correlation candidates |
| Individual health incident | Stable episode, evidence, acknowledgement and notification work | Runtime primary membership and secondary relationship links |
| Condition notification facts | Severity/impact lifetimes, immutable occurrences and original budgets | Exact coverage records between child work and case work |
| Investigation HTTP/MCP | Bounded selected evidence; no consumer execution | Membership, candidates, decisions and audit projections |

Relevant implementation anchors are [conditions](../controller/lib/mondek/conditions.ex), [models](../controller/lib/mondek/models.ex), [notification admission/completion](../controller/lib/mondek/notification_worker.ex), [investigation](../controller/lib/mondek/investigation.ex), [MCP](../controller/lib/mondek/mcp.ex) and [SDK declarations](../runner/mondek_runner/authoring.py). Existing [HTTP conventions](HTTP-API.md), [acknowledgements](ACKNOWLEDGEMENTS.md) and [transaction ownership](TRANSACTIONS-AND-LOCKS.md) constrain the implementation.

## Episodes, membership and lifecycle

`attach(parent)` identifies an existing open health episode. If it has no case, create a case containing that episode as the anchor and the new child. If it already belongs to a case, resolve to that case and retain the requested parent in the decision audit. Do not turn the parent health episode itself into an aggregate: its measured recovery remains visible even when affected apps continue failing. The case remains open while any member retains an unresolved failure; close it only with explicit measured-recovery versus withdrawal/reclassification reasons. Anchor recovery does not detach children or claim their recovery.

A case may have no anchor when operators group symptoms before finding an upstream incident. Adding or replacing the anchor is an audited hypothesis change. A new failure after an episode closes is a new episode and needs a new correlation decision; neither membership nor acknowledgement transfers automatically. An open condition episode is a single correlation member; its equivalent contributions cannot be independently moved out of the condition by correlation commands.

Normalize an individual contribution already owned by a condition episode to that condition episode before candidate selection and command review, or reject it explicitly. Never allow effective membership and notification ownership through both the condition and one of its contributions.

Initial topology is a flat case with member-to-anchor presentation, rather than recursively nested cases. Reject self attachment, duplicate membership, closed candidate parents, environment mismatches and conflicting moves. Attaching within the same case is idempotent. A parent already in a different case requires an explicit reviewed move or merge. Default matching requires exact monitored environment, including null as an exact value; cross-source hints require explicit namespaces and cross-environment correlation requires a separate operator policy.

Detachment ends a membership interval, preserving the episode, evidence, own acknowledgement, maintenance and existing notification work. It records an operator override that prevents the same automated proposal immediately reattaching that episode. Re-enabling automation is explicit. Merge moves selected open memberships into a survivor case; split moves selected memberships into a new case or releases them as standalone incidents. Neither operation merges evidence histories, resets budgets, nor copies acknowledgements. Source cases retain history and a redirect/reference to the reviewed successor where applicable.

## Persistence and provenance

Add ordinary Ecto schemas and a `Mondek.Correlations` context, not a general workflow engine. Proposed durable records:

- **Case:** ID, open/closed state, title, anchor reference, topology/attention/acknowledgement revisions, opening/closing times and reason.
- **Health episode reference:** a typed reference with exactly one foreign key to an individual or condition episode; reuse an existing suitable typed identity if implementation inspection permits. Do not use an unchecked UUID that may refer to either table.
- **Membership interval:** case, episode reference, role, start/end, ending reason, decision and revision. A partial unique constraint permits at most one active primary membership per episode. Secondary links have a dimension and explicitly grant no notification inhibition.
- **Decision/audit:** requested and effective operation, previous/new relation, provenance (`declared_rule`, `correlation_rule`, `operator`, `model`), actor, bounded reason, nullable confidence, controller timestamp, rule/model version, input revisions, candidate snapshot and idempotency key. Confidence is model output, not proof of causality; operator decisions need no invented confidence score.
- **Decision request:** durable request identity, episode/revision, bounded candidates and evidence references, deadline, lease/attempt state, response and terminal disposition.
- **Notification coverage:** exact child occurrence/fact lifetime, case occurrence or case acknowledgement scope, membership interval/revision and destination identity. Attempted and accepted coverage remain distinct.
- **Terminal obligation:** original attempted failure reference, exact affected episode/fact and destination, current case/standalone custodian, terminal delivery identity and bounded credit ledger. Ownership changes preserve the obligation rather than inventing recovery or dropping the receiver's eventual closure.

`declared_rule` means an explicit correlation policy evaluated against accepted source hints; it does not reinterpret `Condition` contribution membership as runtime correlation. Hints alone create no membership. Every accepted move, rejection, override, timeout and late response remains inspectable. Retention must preserve references required by open cases, audit and unresolved delivery work, without promising unlimited retention of all observation bodies.

## SDK hints and candidate selection

Add a bounded optional list of correlation hints to an `Output`, with consumer helpers able to apply target-wide defaults. A hint names a dimension, a typed dependency selector and a bounded correlation window. Examples are an app depending on the exact `cluster-network` condition or on a `shared-mysql` target. Condition selectors include namespace/key and exact environment; target selectors use actual target identity and its existing scoping rules, never a display label. These declarations travel through the accepted inventory generation and frozen runner snapshots, with Python/Elixir validation and shared fixtures.

An illustrative shape is `CorrelationHint(dimension="infrastructure", depends_on=ConditionRef(...), window_seconds=120)`. Final public names and byte/count limits require contract implementation; this is not an available SDK call. Initially allow at most sixteen hints per output, matching only explicit identities. Attribute-based selectors can follow with a bounded, typed, versioned set of exact attribute predicates; do not add a general query language or infer dependencies from arbitrary target keys. Preserve `CheckGroup` browsing semantics. An app can have app, network and database relationships simultaneously, but only one selected primary case can inhibit delivery.

Candidate retrieval is controller-owned, indexed and bounded, with explicit truncation and ranking reasons. Supply up to twenty exact candidate episodes, prioritize declared dependencies, and record an omitted count, truncation reason and bounded sample rather than every omitted identity. Similar time or text alone is a suggestion, never equivalence. The time window compares labelled evidence/detection times with explicit missing-time handling; it is a candidate heuristic and cannot prove physical onset. An old, still-open upstream outage remains a possible parent when a child starts later, so the window must include an ongoing-overlap rule rather than rejecting every old parent.

Persist hints and identity provenance from the configuration that authorized the opening evidence. A later inventory change can initiate a new reviewed decision, but must not silently reclassify an old episode. Opening an upstream incident also searches a bounded set of recent standalone episodes for possible late attachment. This handles apps reporting before the network check. It never extends their original notification deadline; already sent alerts cannot be recalled.

For a shared condition episode, no first contributor owns hint policy. Build a deterministic bounded union of hints from its admitted contributions, retaining each contribution's accepted-generation provenance. Conflicting proposed parents remain alternatives with explicit conflict/truncation information; automatic attachment abstains when a configured deterministic policy cannot resolve them. Later contributions can trigger fresh evaluation, never a restarted hold. The union and its evidence excerpts need their own byte/count limits independent of the twenty-candidate response limit.

## Decision protocol and bounded waiting

User direction: follow the OpenAI Decisions API for the Jev integration. Align the adapter and request/result lifecycle with that API before defining a Mondek-specific transport. The worker claim/submit and lease sketch below is provisional internal fencing design, not a requirement to introduce a competing public decision protocol. Verify the actual API contract during implementation; this proposal does not assume its endpoint shapes or capabilities.

On incident opening, atomically persist an evaluation request alongside existing native incident/notification work. A configured controller policy may place eligible failure work behind a short correlation hold. Correlation is disabled by default; a proposed initial enabled default is ten seconds, with a hard installation maximum of thirty seconds and zero supported. The deadline is persisted from first controller detection, not an untrusted source timestamp. Job retry, controller restart, candidate arrival and repeated `undecided` responses cannot extend it.

The decision input contains the incident identity/revision, scoped selected-output investigation evidence, current controls, accepted hints, bounded open candidates, candidate revisions, truncation and deadline. The output is `attach(parent_episode_ref)`, `standalone` or `undecided`, plus reason, nullable confidence and decider/version identity. A confidence threshold is an operator policy; a model cannot grant itself attachment authority. Run deterministic policies first, then optionally a configured external decider. Persist work in Oban; network/model I/O happens outside database transactions. Consumer Python and arbitrary executable callbacks never run inside the controller.

An external worker claims a bounded lease through a proposed HTTP decision-request API and submits a result with request identity, lease and reviewed revisions. A response after deadline, after closure, after an operator override or against stale membership is recorded but cannot apply as the old request. A fresh later decision can attach an episode under current policy without holding its alerts again. Candidate changes can invalidate an attachment; do not require every irrelevant candidate to remain unchanged.

At the exact deadline, timeout, unavailable decider, invalid output or repeated undecided result releases the original work as standalone. Correlation holds consume no receiver attempts. A lease timeout is bounded by the same deadline; automatic request retries are separately bounded and never renew it. This gives Jev an integration point without making incident detection or notification availability depend on an LLM.

## Notification semantics

The objective is one initial correlated notification per destination when decisions settle before dispatch, with further attention for meaningful escalation. It is not a promise of exactly one message for an outage: impact updates, independent delivery destinations, late correlation and already-started I/O can produce additional messages. Existing at-least-once delivery and ambiguous receiver acceptance remain visible.

The original child occurrence, payload, destination, evidence age, attempts and budget remain intact. Do not mark work delivered or irreversibly superseded merely because a model attached its incident. Case delivery uses its own immutable payload that names exact member evidence/fact lifetimes and the requested severity/impacts. Adding members cannot mutate a previously queued payload or retroactively make an accepted payload cover evidence it never named.

The concrete handover rule is:

1. Membership alone does not inhibit delivery beyond the short decision deadline. Transactionally reserve compatible eligible child work into case delivery with an explicit bounded handover deadline; persist the exact coverage map and one aggregate delivery budget. Persist a first handover expiry on the original work, proposed as thirty seconds from first reservation; later attach/detach/merge/split cannot renew it. Reservation never replenishes any child's budget.
2. While case delivery has live budget and its handover deadline has not passed, reserved child work waits. If case delivery fails permanently, exhausts its budget or misses that deadline, release uncovered original child work with its remaining budget. A broken aggregate sender must not silence all children indefinitely.
3. Accepted case delivery records coverage only for the exact reserved lifetimes and matching destination snapshot. A newer child lifetime or changed destination is uncovered. An individual delivery that was already accepted may satisfy that exact fact; do not create a second initial case message solely to restate it.
4. Detachment or split invalidates active suppression/acknowledgement coverage derived from the ended membership. Pending original work becomes eligible subject to its own controls; original delivered/exhausted work stays delivered/exhausted. Accepted case coverage remains historical delivery evidence, so detaching does not resend facts already conveyed. No topology change silently grants a fresh budget.

Fence each original occurrence with one durable delivery owner/reservation epoch. A child with a started unresolved native attempt cannot be reserved into a case. An admitted aggregate attempt freezes its exact reservation set and evidence references. Detach/split ends membership immediately but does not start competing native delivery for those reservations until that already-admitted attempt settles or is classified ambiguous after the bounded transport deadline. Completion records exact coverage for the frozen set even if membership has since ended; it cannot cover newly attached members or revive old acknowledgement scope. Failed or ambiguous completion releases remaining credits under current membership. Controller recovery reconciles abandoned admissions before reassigning ownership. Never wait for I/O inside the topology transaction. Receiver duplicates remain possible after ambiguous I/O, as with existing delivery, but concurrent native and aggregate ownership is prohibited.

Completion locks native owners from its frozen reservation snapshot, including members that have since moved, before case/occurrence rows. A stale completion can record late acceptance of its exact evidence but cannot reclaim newer ownership, overwrite a newer accepted status, debit credits again or revive a released reservation. Fencing database writes cannot retract old receiver I/O.

Use an explicit durable automatic-attempt credit ledger per original occurrence; Oban's own job attempt counter is insufficient for shared budget accounting. At reservation, aggregate attempt cap is `min(configured_case_cap, min(remaining_child_credits - 1))`. Reserve only when that cap is positive, retaining at least one original-delivery credit for each child on failure. At aggregate admission, durably debit one credit from every covered reservation before I/O; ambiguous attempts spend credits too. Releases and repeated topology changes cannot multiply credits. Existing work must derive its initial credits from its original bounded delivery policy and recorded attempts, never today's higher configured limit. Manual retry is a separate explicit audited action under the existing policy. Only compatible destination/channel snapshots share a delivery; never reroute existing work to today's configured receiver. Partial eligibility cannot authorize a payload that includes maintained or otherwise ineligible facts.

A case acknowledgement captures reviewed case revision, severity ceiling and a **member-qualified impact set**, expiry and operator note. Existing impact keys are meaningful within their original episode/condition; equal strings on unrelated apps are not automatically equivalent. Above-ceiling severity or a newly uncovered member-qualified impact ends the case acknowledgement irreversibly and requests renewed attention. New members within the severity ceiling and without new material impacts may derive coverage from an explicit case-wide ongoing-outage acknowledgement, and the UI must state that scope. Ordinary child acknowledgements remain unchanged. Merge/split cannot broaden a survivor's acknowledged scope without review; unresolved newly exposed facts invalidate it.

For unacknowledged cases, introduce a distinct ongoing **case attention lifetime** for each severity threshold and normalized impact identity. An accepted notification can establish delivery of that lifetime for its destination; it does not establish delivery of future children's exact evidence. A later attached child at an already delivered severity, without a new impact, maps to that still-open attention lifetime through a durable correlation-suppression record and adds no notification. The original case payload must explain this ongoing scope and link to live affected-member detail. A new severity threshold or material impact opens new attention and generates an update; scope ends on case closure and never transfers to another case. Pending attention still needs bounded reservation/fallback, and exhausted attention cannot suppress new child work. Show `correlated_under_delivered_case_attention` separately from `included_in_accepted_delivery` and acknowledgement coverage. A detached late child with only ongoing scope coverage releases its original work, because its exact evidence was never conveyed. If Mondek cannot prove any of these coverage bases, send an update or release the child.

This ongoing inhibition is a new, explicitly operator-enabled policy, separate from both receiver acceptance and human acknowledgement. Default to exact batched coverage until it is enabled. Activate it only after accepted initial case delivery, persisting its policy version, dependency scope, severity/impact baseline and first expiry. Propose a fifteen-minute default with a one-hour hard maximum for unattended policy; members, retries and topology changes cannot renew it. New impact, above-ceiling severity, anchor/hypothesis change, merge/split, policy change or scope departure ends this coverage and wakes still-pending original work without replenishing budgets. Expiry falls back to exact batching or original delivery; a human can instead explicitly acknowledge the ongoing case. Show the policy scope and expiry in both UI and notification payload. This accepts a finite risk of miscorrelation in exchange for fewer repeat alerts; it must never label late evidence delivered or acknowledged. If these controls are not ready, the first release supports exact batches plus explicit case acknowledgements only.

Impact identity defaults to member-qualified keys. A versioned correlation policy may explicitly map selected source/condition/impact keys into a shared case impact identity when the operator intends the same material consequence across apps. Equal bare keys or model-supplied prose cannot do this implicitly. Consequently, dozens of children adding only the existing severity can produce one initial notification, while dozens of genuinely new material consequences may produce updates. Exact mappings and their policy versions belong in the attention and decision audit.

Maintenance continues to gate each underlying fact. A maintained CRIT cannot justify a CRIT case notification supported only by an uncovered WARN, and maintenance on the anchor cannot hide unmaintained children. Show measured aggregate severity separately from eligible notification severity. A case closing before any failure attempt produces no misleading recovery message. Otherwise case closure follows existing attempted-delivery rules; do not emit dozens of child recovery messages for failures communicated solely through the case. Previously independently attempted child notifications retain their own closure obligations. Anchor recovery is an update, not case recovery.

Extend those closure rules with durable terminal-obligation custody: when a failure is first attempted through a case, persist the affected episode/destination obligations with their terminal identities and bounded budgets. Detach/split/merge transfers unresolved obligations to the successor case or standalone episode without replaying failure or renewing terminal credits. Aggregate terminal attempts spend the credits of the exact obligations they cover. For example, if B detaches while failing and A recovers, the old case's terminal message says A recovered and B moved but remains unresolved, with a successor link; it cannot claim the whole original outage recovered. B's eventual recovery still closes its transferred obligation even when B never had an independently attempted failure message. Repeated moves cannot discard or duplicate obligations. Terminal-custody support is required before enabling topology edits on attempted aggregate work.

## Transactions, bounds and restart

Keep incident admission and native reduction authoritative. Correlation work is transactional durable work, not a synchronous model call in ingestion. Recheck open state, policy, revisions, controls and membership at apply and dispatch; a read projection cannot authorize mutation. Use unique constraints for active membership, request idempotency and coverage identity. Multi-member commands are atomic and bounded; propose a first case limit of 250 active member episodes, rejecting larger merges explicitly rather than silently truncating controls. Paginate historical membership; separately bound per-command selected IDs, secondary links, audit excerpts and notification payload bytes. Condition contribution fan-out can exceed the case member count, so that count alone bounds neither query work nor locks; qualify those paths explicitly and reject oversized atomic operations before mutation.

The new cross-episode lock graph requires an explicit extension to the current lock contract before code lands. Proposed starting point: a transaction-scoped topology gate, shared for membership-sensitive native writers/dispatch and exclusive for attach/detach/merge/split. Keep any configuration-repository lock outermost, maintenance before topology when both are needed, topology before native assignment/condition ownership, and case rows before occurrence rows. Topology edits precompute the complete member ownership set under the gate, lock sorted assignments and condition stripes in existing order, then sorted cases and affected work. Never acquire another member's native owner after locking a case or occurrence.

Ingestion can enqueue case reconciliation without locking other members; a reconciliation/dispatch worker acquires the full bounded native ownership set before reducing case attention or reserving work. A stale asynchronous case projection grants no suppression: dispatch must verify current member revisions or release work at its deadline. Completion, acknowledgements, maintenance, retirement, retention and recovery require the same ownership analysis, including implicit foreign-key locks. Prototype this ordering with controlled PostgreSQL races before treating it as a settled implementation; a global exclusive topology edit may warrant a finer mechanism only after correctness and contention measurements.

All deadlines, reservations, decisions and wake revisions survive restart. Hold changes wake existing jobs. Retention cannot delete active references or pending original work. External notification/model calls remain outside transactions. Audit rejection and duplicate receipts need bounded storage and safe diagnostics.

## Operator UI, HTTP and MCP

The incident list renders a case as one expandable operator row with aggregate and matching counts, retaining child navigation and filters that find a member without shrinking aggregate scope. Detail shows suspected anchor, independent member evidence, freshness, individual controls, acknowledgement coverage, partial maintenance, held delivery and decision history. Label correlation as a hypothesis, including confidence/provenance; never relabel it confirmed root cause.

Provide reviewed attach, detach, merge, split and anchor-change actions, with exact selected episode IDs, revisions, a reason, previewed notification consequences and idempotent apply. Use explicit `/api/v1` resources for cases, memberships, candidates, decisions and decision requests; follow generated schemas, bounded pagination and existing error envelopes. Final path names belong to API implementation, not this proposal. Stale review returns a conflict, never an implicit replanning of a destructive multi-member command. Existing health endpoint identities remain addressable.

Extend read-only MCP investigation with the same bounded projections and candidate/decision context. Keep MCP mutation capability unchanged in the first version: an external decider reads via HTTP/MCP and submits its leased decision through the dedicated HTTP protocol. Adding generic MCP attach/detach tools later would require an intentional change to the documented read-only boundary. HTTP mutations retain the existing isolated trusted deployment assumptions; a worker lease is concurrency fencing, not authentication. No external model receives evidence until explicitly configured by the operator; send selected bounded evidence, not raw snapshots or private configuration values, and treat all consumer text as untrusted data.

Case fly-over and full page must render one shared entity body with LiveView parity coverage. Verify desktop and narrow layouts through the real app, preserving unsaved operator review state across refresh and reconnect.

## Delivery plan and acceptance gates

1. **Native model and investigation:** schema/migrations, typed references, membership/audit, manual reviewed controls and HTTP/MCP reads. Ship with correlation notification inhibition disabled. Preserve existing installation history and update startup upgrade guidance.
2. **Notification handover:** case attention/facts, precise acknowledgement scope, reservations, immutable coverage, budget accounting, dispatch gates, fallback and terminal-obligation custody through moves. Resolve the lock prototype, finish an exhaustive transition table and qualify crash/restart behavior before enabling this feature.
3. **Deterministic automation and SDK hints:** accepted-generation hints, bounded candidate search, late-parent reconciliation and time-bounded requests. Preserve old declarations unchanged; update SDK exports, inventory/snapshot validators, protocol fixtures and authoring guides together.
4. **External decider:** integrate Jev following the OpenAI Decisions API, retaining Mondek-owned deadlines, stale-response fences and reviewed mutation semantics. Reconcile the provisional worker/lease sketch with that API rather than establishing a competing protocol. Start in shadow mode with proposals and operator acceptance; automatic attachment is a separate operator policy. Jev stays external and replaceable.
5. **Additional dimensions/selectors:** noninhibiting relationship facets first; promote attribute-based candidate rules only with explicit identity/scoping and bounded query contracts. Do not quietly introduce multiple suppression parents.

Required meaningful tests include both parent/child arrival orders; concurrent opposite attachments and merges; per-episode recurrence; anchor recovery with failing children; condition members; exact hold expiry; stale/late/duplicate model replies; override persistence; new severity/impact within and beyond acknowledgement scope; partial maintenance; distinct destinations; fallback after case exhaustion; detach after partial attempts or accepted case delivery; repeated moves without replenished budgets; closure obligations; controller death between admission/I/O/completion; and migration/retention with pending work. Cover transactional behavior with real PostgreSQL and controlled interleavings, installed SDK/controller flows with local webhook receipts and restart, serialized HTTP/MCP bounds and real browser controls at both widths. Existing standalone and shared-condition suites remain regression gates. No live notifications or external deployment changes are needed for qualification.

The key design decisions are therefore separation from equivalence, durable case identity independent of the suspected parent, one suppression owner, finite waiting, exact evidence/delivery accounting and an external advisory decider. The principal implementation risk is the notification and locking extension, not selecting or calling a language model.

## GPT-6 Astra design review

Reviewed by a GPT-6 Astra agent on 2026-11-16 against the current condition, acknowledgement, lock and delivery contracts. The review endorsed the separate case model, flat topology, independent child evidence and external advisory decider. Its material findings were incorporated: reserve a fallback delivery credit, fence in-flight ownership and completion, transfer terminal-obligation custody, explicitly opt into finite ongoing inhibition, normalize condition contributions, combine their hints without first-observer ownership, and bound omitted-candidate/audit data separately.

This is a reviewed proposal, not an implementation qualification. Before phase-two code is enabled, write the full transition table for admission, accepted/failed/ambiguous completion, late completion, detach/merge/split, attention expiry and terminal custody, and prove the proposed lock order with real PostgreSQL races. Flat cases intentionally preserve the requested immediate parent in audit rather than maintaining a nested causal tree. Timing/count defaults above are proposed starting points requiring qualification, not measured capacity claims.
