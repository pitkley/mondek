# Correlation hints, relationships and decisions

Draft for operator review, 22 November 2026. Start from [manual correlation cases](RUNTIME-INCIDENT-CORRELATION.md) and [exact batch delivery](EXACT-BATCH-DELIVERY.md). The three design topics share one incident model, one candidate policy and one review boundary. The earlier [correlation proposal](RUNTIME-INCIDENT-CORRELATION-PLAN.md) provides background. Current delivery behavior follows the shipped contract.

## Incident relationships

A `Condition` owns equivalent measurement evidence. A correlation case groups independently measured health episodes that may share a cause. Reuse the existing canonical individual or condition episode identity and exact monitored environment. A recurrence gets a new episode. The case stays flat, with at most one primary membership per episode. A recovered parent stays visible while a child still fails.

A secondary relationship is a directed link between two exact episodes in a named dimension, such as application, network or database. An episode may have several links. Store the dimension, endpoints, disposition, and accepted rule or reviewer and evidence provenance. Give these links their own revision and history. Display their endpoints independently, including recovery or detachment. An active link ends when either episode closes or an operator removes it. Investigation shows links as hypotheses and avoids treating a chain of links as inferred evidence. Secondary changes leave primary topology, case acknowledgement, batch eligibility, destinations and retry credits unchanged.

## Candidate selection

An SDK hint proposes an exact dependency selector and a dimension. Start with existing Condition and target identities, including exact environment and the namespaces those identities require. Give each hint an explicit bounded time window for recent matches and an overlap rule for a still-open upstream incident. Treat display labels and explanatory text as evidence for inspection. Bind each hint to the measured episode contribution and accepted inventory generation that supplied it. A declaration refresh can initiate a new evaluation without rewriting provenance of earlier evidence. For a shared Condition, merge admitted contributions deterministically, include conflicts and truncation, and abstain from automation when the evidence is incomplete or conflicting. Resolve a selected contribution to its canonical Condition before deduplicating.

The controller builds bounded, ranked candidate sets with exact episode references and reasons. A child opening evaluates existing upstream episodes, including older episodes still open. A parent opening reevaluates a bounded set of recent standalone children. Use controller detection times for the arrival window and expose evidence times separately in investigation. A late match may create a proposal, including after dispatch. Candidate limits, ranking and ties need fixtures before implementation. Read projections distinguish absence of a match from a truncated or unavailable search.

## Decisions

A decision evaluates one episode against a frozen candidate list. A deterministic rule or a configured provider can produce a decision. Mondek owns candidate eligibility, evidence disclosure, notification policy and every topology change. Record the producer's verified identity, rule or adapter version, input revision, reason, disposition and controller time. A provider's reason and optional confidence are advisory evidence.

Use one versioned internal request and result format. A request records its identity, subject episode, relevant evidence and topology revisions, policy revision, ordered eligible candidates, completeness flags, and an absolute expiry. Allow the result to suggest one supplied candidate, suggest leaving the episode standalone, or abstain. Selecting a candidate creates a proposal. A standalone suggestion expresses a provider judgment for this request. Neither creates a persistent episode override. Eventual desired support for independently configured providers is compatible with starting with one adapter and a deterministic fixture. Verify the selected provider's supported contract before choosing its transport or request mapping.

The first provider integration runs in proposals-only mode and sends bounded allowlisted evidence to an explicitly configured destination. Use request-local candidate handles, omit private configuration, credentials and raw evidence, and treat consumer text as data. Store the producer identity from the adapter configuration, independently of the response body. Bind the adapter configuration revision, authorized destination and exact disclosed payload to the request. Check current disclosure authorization before every outbound admission, including retries. A changed destination or adapter configuration requires a new request. Revocation blocks further admissions and invalidates unapplied responses to an earlier disclosure policy. A pull API would need its own authenticated principal and evidence scope. The existing investigation MCP stays read-only.

Persist request identity, expiry, and the terminal result or disposition. A job may retry an outbound request within the original expiry, reusing its identity where the provider supports idempotency. Mondek accepts at most one result per request, returns the saved disposition on exact reply replay, and rejects conflicting replies. For advisory review, an unrelated candidate change leaves a still-eligible selected candidate available. An expired request, changed policy, closed episode, stale selected relationship, or intervening operator override prevents an old result from taking effect. Routine unchanged failure evidence can advance observation history while the decision remains applicable. Run network I/O outside the database transaction. Unavailable providers and invalid or late responses leave manual grouping and native delivery available.

Accepting a provider proposal starts the existing reviewed create or attach flow. Revalidate the relevant subject, selected parent, policy and operator revisions before review and again when applying. Record the proposal ID with the accepted action. Initial provider proposals can cite only primary candidates. Secondary links can use the same candidate evidence and provenance without waiting for a provider.

## Authority and delivery

A manual detach or a reviewed keep-standalone action should create an episode-scoped automation override. Subsequent rule evaluations and provider replies respect it until explicit re-enablement or the episode ends. Existing manual cases and memberships remain under operator control. Manual override, candidate results and the automation apply path must serialize with the same relevant topology and native owners. Discovery alone grants no authority.

For the first automatic primary slice, propose allowing an explicitly enabled deterministic rule to create a case from two standalone episodes. Start cases with batching off. Require a fresh, complete search with exactly one eligible parent. Check for an active native acknowledgement or maintenance hold, any outstanding reservation including work from an earlier membership, any delivery attempt including ambiguous work and previous retry epochs, and an operator override. A conflict or incomplete search leaves a proposal for review. Moves, merges, splits, and anchor changes use manual review.

Candidate uniqueness must hold at commit. Design the transaction so relevant incident openings, closures, accepted hint and rule changes, operator actions, maintenance, and dispatch admissions serialize with the apply check. The existing topology lock covers topology edits. Verify the additional writers and race cases before enabling automatic apply. If the controller cannot establish uniqueness within the bounded search, the path ends with a proposal.

Extending an automation-created case can follow once there is a persisted ownership fence. A manual membership or anchor edit, or any operator case control, transfers it to operator ownership, including a later return to batching off. Recheck ownership and every current member, including recovered ones, with the same controls and delivery fences. Until then, suggest adding further members through manual review.

Propose manual review for secondary links initially. If a later rule may add them, specify an episode-pair and dimension override so a removal can survive reevaluation.

The first advisory and automatic slices introduce no discretionary hold. Existing queued evidence, destinations, credits, and terminal identities keep their original scope. Any future notification hold needs its own operator policy, a shared absolute ceiling with discretionary send windows, standalone fallback, and a transition review with recipient routing. Exact batching continues to use its existing destination compatibility, frozen reservation and handover rules. Its terminal obligation remains attached to the original attempted episode set and destination until the last of those episodes ends. Secondary links never confer receipt coverage.

## Walkthroughs for design review

| Scenario | Expected operator and delivery behavior |
| --- | --- |
| App fails first, then the network incident opens | A bounded recheck can show the network candidate, including after the app alerted. Early automatic grouping can proceed only if both episodes still pass the apply fences. Standalone delivery keeps running on its original schedule. |
| The database and network incidents are both plausible | Show both dimensions, their reasons, and any shared Condition disagreements. The operator can accept independent secondary links. An ambiguous primary match stays a proposal. |
| An operator detaches an episode while a provider request is outstanding | A sticky override makes the old reply inapplicable. The detached episode keeps its own evidence and unchanged delivery identity. The reason and disposition remain inspectable. |
| A and B were attempted together, then B moves and A ends | The original A+B terminal obligation remains pending for the original destination. When B ends, the terminal payload covers the original pair and their closure reasons. Any independently attempted native work retains its own terminal path. |
| The controller restarts after sending, or a provider replies after expiry | Retry can reuse the original request identity and expiry. Only a fresh compatible result qualifies for review. No retry, response, or reconciliation extends a notification deadline. |

## Proposed slices

1. **Hints and candidate inspection.** Ship SDK and accepted-inventory provenance with bounded read projections for HTTP, MCP and the operator UI. Test both arrival orders, older open upstream episodes, shared Condition disagreements, canonical deduplication and truncation.
2. **Secondary relationships.** Reuse ranked candidates in an operator-reviewed link flow. Show dimensions and provenance. Verify that adding, ending or inspecting links leaves case revisions and notification eligibility unchanged.
3. **Deterministic primary attachment.** Implement explicit rule opt-in and durable manual overrides. Prove that a competing upstream opening, a changed hint or policy, an override, or a dispatch admission cannot invalidate the apply check, using real PostgreSQL. Include a detach during batch admission so a returned standalone episode cannot evade the reservation fence. Preserve standalone timing and all existing delivery receipts.
4. **Provider decisions.** Qualify a real adapter against its supported interface, plus a fixture for outages, stale and conflicting responses, replay after restart, and evidence disclosure. Start with proposals and reviewed acceptance. Explore implementation in parallel with slices 2 and 3 once candidate and proposal contracts stabilize.
5. **Optional delivery or authority extensions.** Review provider-driven automatic attachment and any correlation hold separately. Require decided defaults, scoped routing and preservation of original budgets and terminal obligations for changes that affect recipient delivery.

Review the operator walkthroughs and proposed defaults before implementation. The first design decision is whether opt-in deterministic grouping may create a case before either side has attempted delivery. Automatic extension has a separate ownership and concurrency gate. The second is whether secondary links should start with explicit review only or also be eligible for deterministic rules. The third is what evidence categories an operator can explicitly permit for provider decisions.
