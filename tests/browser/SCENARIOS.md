# Browser scenarios, evidence and limits

Run `devenv shell -- mondek browser`. This starts fresh, sequential Compose projects: the three-check source consumer, measurement investigation through real collection/transport failures, monitoring-loss notifications, a fifty-runner inventory with twelve live observers and dedicated delivery investigation, an empty installation, the multi-runner demo with 500 additional file results, 500 independently scheduled checks with compatible delegated parameters, durable rules across two node observers, project-managed policy, incident acknowledgement workflows, scheduled maintenance, grouped target inventory, source-defined browsing groups, shared incidents from independent storage observers, pre-selection coverage declarations, reviewed publisher lifecycle actions, and source-defined discovery review against real directories. Each project has independently allocated loopback ports, PostgreSQL/runner/fixture volumes, and its own local notification receiver. The wrapper always removes its own services and volumes; it does not reuse or reset the normal demo.

For one suite, run `devenv shell -- python3 tests/browser/run.py --suite lifecycle`, `--suite diagnostics`, `--suite monitoring-loss`, `--suite fleet`, `--suite empty`, `--suite parity`, `--suite bulk`, `--suite rules`, `--suite policy`, `--suite acknowledgements`, `--suite maintenance`, `--suite inventory`, `--suite check-groups`, `--suite grouped`, `--suite coverage` `--suite publishers` or `--suite discovery`. Runs build the packaged application and browser image, so the first run downloads browser dependencies. No host browser installation is required.


For a persistent manual publisher lifecycle walkthrough, run `devenv shell -- mondek publishers` and open [Runner declarations](http://localhost:4017/coverage/publishers). This uses its own project and volumes; `devenv shell -- mondek publishers-down` stops it while retaining history. `devenv shell -- mondek publisher-acceptance` runs the destructive restart/reconnect scenarios in a separate disposable project.

The browser shares its own isolated controller's network namespace and opens `http://localhost:4000`. This gives Chromium a genuine loopback secure context, matching local use without weakening browser security flags. Fixture calls still use the same project's `target` service. The prompt-copy journey grants clipboard permissions, checks the actual clipboard contents after a keyboard action, then rejects a write to verify the selectable-text fallback.

Operator journeys use the live UI. Read-only API requests corroborate observation and notification identities; fixture calls change only the owned local target/receiver. Bulk and rule journeys additionally use the public configuration API to create a concurrent operator edit; the bulk journey also crosses real thresholds for thirty selected checks after the 500-check UI save. Maintenance journeys use its public API to introduce an independent overlap or concurrent child edit, reject an attempted change to saved scope and verify stale cancellation rejection. Draft-recovery tests use the application's exposed `liveSocket` only to disconnect and reconnect transport, verify disconnected/reconnected state, and never inject form state. Browser assertions use eventual state with bounded waits, with no hidden automatic retries of failed journeys.

## Artifacts and limits

The fleet journeys are `devenv shell -- python3 tests/browser/run.py --suite fleet`. One disposable container supervises ordinary runner CLI processes with at most twelve active at once. Each uses one worker, a thirty-second schedule and a separate persistent state directory; startup is staggered. After twelve live observers exercise failure, recovery and restart, additional observers publish and measure in bounded batches. The final inventory contains fifty runners with real measurement history: twelve live and thirty-eight stopped with ageing contact and results. Fixture HTTP controls only manage those actual processes and datasource responses; they do not manufacture controller inventory, observations or notification rows. The fleet fixture uses fifteen-second contact, one-hundred-second collection freshness and sixty-second loss grace. Keep other heavy acceptance runs stopped until this owned project cleans itself up. Fifty simultaneous full CLI processes exceeded measurement deadlines on the shared Docker VM during exploratory runs. This bounded suite establishes operator flows with fifty runners and operation with twelve live runners. Recovery with fifty concurrent runners and production capacity are not established.

The focused measurement investigation journey is `devenv shell -- python3 tests/browser/run.py --suite diagnostics`. It uses the real installed demo runner and datasource timeout, then partitions only controller transport while collection continues. It checks contextual return navigation, safe agent prompts, live recovery, original-age buffered reports, reconnect and desktop/320px accessibility.

The monitoring-loss journeys are `devenv shell -- python3 tests/browser/run.py --suite monitoring-loss`. Only this disposable suite shortens loss grace to six seconds and runner contact to five seconds; initial measurement still receives the controller's cadence-based minimum. The default installation delays remain unchanged. The wrapper runs a first browser phase, restarts its owned controller with an acknowledged loss and held notification, then opens a fresh browser to verify persisted identity, unchanged retry budget and actual delivery/recovery. The second phase has a separate `restart/report/index.html` report. All failures use real worker execution, controller transport or local receiver behavior; no database rows or monitoring events are fabricated.

Each `.local/browser/mondek-browser-*/` directory contains a summary with project/ports/cleanup status, Compose build/run logs, bounded service logs, a Playwright HTML report, JSON results, screenshots, accessibility scan attachments, and failure video/trace. Fleet runs additionally retain the last 20,000 controller log lines so early scale-up failures remain inspectable after cleanup. Open the HTML report locally; run `devenv shell -- npm --prefix tests/browser ci --ignore-scripts --no-audit --no-fund` and `devenv shell -- npm --prefix tests/browser exec -- playwright show-trace --host 127.0.0.1 <trace.zip>` to serve a retained trace for inspection in an existing browser with the pinned package. No host Playwright browser installation is needed. These artifact directories are ignored by Git.

The suite runs Chromium on Linux; this is repeatable browser regression coverage, not a cross-browser certification or a human accessibility audit. Automated checks cannot establish whether a person understands the product or can use it with every assistive technology. Human operator and accessibility research remain separate work.

## Dependency pins

The [official Playwright Docker guidance](https://playwright.dev/docs/docker) requires the browser image and test package versions to match. `@playwright/test` is pinned to 1.63.0 and the corresponding official Noble image is pinned by its multi-architecture manifest digest (Linux ARM64 and AMD64). `@axe-core/playwright` 4.13.0 follows the [official accessibility testing integration](https://playwright.dev/docs/accessibility-testing). Both were checked against their package registries on 2009-09-15; the committed npm lockfile also pins their transitive dependencies. Update the image, package, and lockfile together.
