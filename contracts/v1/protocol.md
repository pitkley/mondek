# Monitoring protocol v1

This is the current experimental protocol family. See [versioning and fixture tests](../README.md) for what v1 means, which fixtures run in both languages and the limits of that evidence. This document does not generate runtime validators or promise interoperability between arbitrary source revisions.

## Runner-provided source inventory

`POST /api/v1/inventory` registers or reconciles `{version: 1, installation_id, session_id, boot, runner_label, source_id, inventory_revision, source_revision, complete: true, checks: [...]}`. Session/boot admission is identical to control. Inventory revisions are positive monotonic integers persisted by the runner per source; an identical revision with identical semantic payload is idempotent, a changed payload conflicts, and an older revision is stale. Transport session/boot are excluded from the semantic inventory payload. An incomplete/invalid inventory never removes accepted membership. A complete accepted inventory is the source's authority over its own check membership, not authority over another runner or source.

Each check is `{key, label, definition_revision, environment?, environment_label?, params_owner: "source" | "ui", parameter_schema, parameter_contract?, params, interval_seconds, timeout_seconds, freshness_seconds, outputs}`. Its controller assignment ID is stable for the runner/source/check-key binding. `source_revision` and `definition_revision` are lowercase SHA-256 digests identifying prepared source and exact binding metadata. Checks load locally by source key; the controller never imports Python. `environment` is a stable grouping ID, independent of the optional display `environment_label` (which defaults to the ID). A label requires an ID. Renaming a label preserves check, stream, group and incident identities. Current metadata follows accepted inventory; retired streams and incidents retain their recorded grouping. Environment filter values are IDs and facets return `{id, label}` entries, choosing one deterministic label per ID. The receipt is `{version, source_id, inventory_revision, accepted_checks}`; desired configurations arrive through control.

`parameter_schema` contains `fields: {name: {type, label?, unit?, minimum?, maximum?, max_length?, choices?}}` and optional `comparisons: [{left, op: "lt" | "lte", right}]`. Supported scalar types are `number`, `integer`, `string`, and `boolean`; values are a complete whole set. There are at most 32 fields/comparisons and 32 scalar choices per field. String values default to a 2048-byte maximum. The source owns executable meaning, target, output membership and schedule; only `params_owner: "ui"` delegates the whole value set. Source defaults cannot overwrite delegated values. Additive schema changes initialize only new fields from source defaults, then validate the complete set with every existing operator value preserved. Removing a saved field, changing its type or units, invalidating its saved value, or reclaiming UI ownership rejects the complete inventory atomically. Existing accepted authority remains intact.

Each complete parameter set has a 16 KiB JSON budget. The controller measures integral numbers after exact decimal normalization, counts non-ASCII text in its escaped form, and conservatively reserves 24 bytes for each remaining fractional float so accepted values fit the Python runner's canonical encoding. Bounds, choices and comparisons use exact decoded JSON numeric values, without float coercion or tolerances. SDK-exported integral floating-point metadata becomes its exact integer value before hashing and serialization; private datasource settings retain their Python numeric types. JSON integer literals, including schema bounds, choices and preserved metadata, have at most 4096 decimal digits excluding a minus sign. This stays within the pinned Python runtime's integer conversion bound without weakening its safeguards. The shared 4 MiB future control-response budget is checked transactionally for both source inventory and operator saves. Saves serialize on the runner before locking checks, so concurrent changes to separate checks cannot jointly exceed the response limit. A rejected save leaves parameters, revisions and configuration history unchanged.

Each output is `{key, label, target: {key, kind, label}}`. It establishes an independent result stream and incident lifecycle. A missing output in a run remains expected and unavailable; partial execution is never an inventory removal. Adding outputs preserves unchanged result stream identities, episodes and acknowledgements. Removing or changing one output target retires only that stream; a reappearing key receives a new stream incarnation. Incidents retain `stream_id` and the exact historical target, while the scheduled assignment advances its configuration generation. Source check withdrawal retires the whole assignment; reintroducing the check creates a new assignment incarnation. A complete source withdrawal retires affected monitoring with an explicit source-removal reason, without measured recovery. Node-local and remote subjects use the same output contract; runner identity identifies observation location, not every target.

All outputs of an invocation share its check-level monitored environment. Output maps, including excluded coverage declarations, must not contain `environment` or `environment_label`, even as null. Such inventories are rejected atomically with a validation explanation; they cannot advance sessions or change accepted membership. Other extension data is not made invalid by this restriction. Declare separate environment bindings for different monitored scopes; see [multiple-environment checks](../../docs/MULTI-ENVIRONMENT-CHECKS.md).

Optional complete pre-selection `coverage` declarations are described in [coverage auditing](../../docs/COVERAGE.md). A publication retired through the [explicit lifecycle](../../docs/OBSERVER-LIFECYCLE.md) is fenced with `publisher_retired`. Restoring it requires a newer inventory with the exact requested `restoration_revision`; control's optional `inventory_refresh` map carries each source's `after_revision` and `lifecycle_revision`. These transport markers do not change consumer semantic source identity. Inventories that cannot satisfy a waiting restoration receive `publication_refresh_required`.

Bounds are 512 checks per inventory, 16 outputs per check and a 4 MiB inventory body. Source IDs, check keys, output keys and target keys are 1–200 UTF-8 bytes without control characters; target kinds are at most 64 bytes, labels (including environment labels) at most 200, environment IDs at most 128, and parameter field names at most 128. Interval is 0.1–86400 seconds, timeout 0.1–300, and freshness 0.1–172800. Generic source assignments use `kind: "python"`; control retains the existing assignment shape and adds `source_id`, `source_key`, `source_revision`, `definition_revision`, `environment`, `environment_label`, `params_owner`, `parameter_schema`, and `outputs`. `prepared`/`active` maps and authoritative control membership cover only the requesting runner's assignments, with a maximum of 512 per runner. Original report and retry identities remain unchanged.

All timestamps are UTC ISO-8601 strings with microseconds. IDs are UUID strings. New assignments receive generated UUIDs independently of their check kind. Runner JSON requests and responses carry `version: 1`. Configuration generations are integers from 1 through 2147483647. HTTP is restricted to loopback/private Compose. API writes require `Content-Type: application/json`; browser form media types are rejected. Unknown versions and malformed or oversized requests fail explicitly. Ordinary requests have a 256 KiB maximum; inventory alone allows 4 MiB. The accepted configuration must also fit a 4 MiB control response. There are at most 32 reports and 16 results per report; summaries and diagnostics are at most 2048 UTF-8 bytes.

## Control

`POST /api/v1/control` takes `{version, installation_id, session_id, boot, status, prepared, active, wait_seconds}`. Control returns only active source-owned assignments for the requesting installation. The installation UUID persists in SQLite; each process start atomically increments durable `boot` and creates a session UUID. Same boot/different session and lower boot control requests conflict. A higher boot fences prior session authority. Status includes `queue_count`, `queue_bytes`, `oldest_at`, `dropped`, `running`, and `diagnostic`. `prepared` and `active` map assignment IDs to integer generations. `wait_seconds` is bounded to 0–10. No transaction remains open while waiting.

The response is `{version, assignments_authoritative: true, assignments: [...], authorized: {assignment_id: generation}}`. Each complete assignment is `{id, kind: "python", source_id, source_key, source_revision, definition_revision, generation, params, interval_seconds, timeout_seconds, freshness_seconds, expected_keys}`. The complete list contains at most 512 active assignments belonging to that runner, with unique IDs and authorization entries belonging to that list. The explicit authority marker permits the runner to remove omitted assignments atomically from its accepted journal and future scheduling. Invalid or partial responses cannot delete accepted state; responses without the marker do not authorize removal. In-flight original evidence survives removal, and offline execution continues the last accepted schedule until control reconciles.

Defaults: filesystem params `{path: "/", warn_percent: 80, crit_percent: 90}`, HTTP `{url: "http://target:8080/ready"}`, consumer `{url: "http://target:8080/data", warn_count: 5, crit_count: 10}`. Expected keys respectively `["capacity"]`, `["readiness"]`, `["backlog"]`. Demo interval is 3 seconds, timeout 2 seconds, freshness 12 seconds. The kind selects implementation; the ID selects independent execution state and evidence history.

The runner validates/prepares exact desired assignments outside control transport; a prepared receipt authorizes only the still-desired generation, transactionally cutting off old evidence. The runner persists an authorized configuration before adoption, freezes it per run, and reports active separately. Preparation errors retain prior accepted scheduling and appear in status. Controller restart never changes generations. Higher boot alone never implies coverage.

Optional `status.scheduler` reports a single local snapshot: `active_checks` is accepted scheduling membership, `running_checks` is currently executing work, and `max_concurrency` is its configured worker bound (at most 16). `due_waiting_checks` counts due accepted checks excluding running or retired work. `oldest_due_seconds` is the nonnegative monotonic delay of the earliest such due run, or zero when none wait. `preparation_pending_checks` counts desired configurations without matching prepared candidates, including preparation in progress. `prepared_waiting_checks` counts prepared desired candidates not yet active. Check counts are bounded by 512. These facts describe scheduling and preparation pressure at the last status report; they do not establish fresh monitoring coverage or predict when all work will finish.

Target paths/URLs are fixed after creation; operator saves can change the filesystem and queue thresholds. An unchanged valid save retains the existing revision/generation, but still rejects a stale reviewed revision. `observed_generation` records only fresh complete measurement evidence; the UI calls this milestone Measured and separately displays present measurement freshness.

## Evidence

`POST /api/v1/observations` takes `{version, installation_id, session_id, reports: [...]}`. Envelope session must be the current transport session; each buffered report retains its original session. Each report is `{id, assignment_id, installation_id, session_id, generation, sequence, started_at, evaluated_at, results, complete, diagnostic}`. Sequence is monotonically allocated and committed before execution, independent of transport, across local restarts. Results are `{key, health, summary, value, source_at}` with health one of `OK`, `WARN`, `CRIT`, `UNKNOWN`; value is a number or null and source_at is a timestamp or null. Failed/missing collection is `complete: false` and cannot erase expected membership or claim recovery.

Results may additionally contain `details`, nullable plain UTF-8 text of at most 16,384 bytes without NUL. The SDK omits the field when no details are supplied, retaining older report shapes. Details are immutable evidence: changing them under the same report identity conflicts. They count toward existing worker, report and spool limits. The controller keeps `current.details` with the last confirmed measurement and `current.execution_details` with the newest execution; failed or stale collection cannot attach its diagnostic text to retained health. A new confirmed result without details clears earlier details. The UI renders details as escaped plain text in result and incident inspection, without interpreting HTML or Markdown or copying the full text into notification payloads.

The response is `{version, dispositions: [{id, disposition}]}` after commit. Dispositions are `current`, `historical`, `duplicate` (optional `original_disposition`), `conflict`, or `rejected`. Semantic identity is complete decoded JSON equality independent of object-key order, transport session or batch packing. PostgreSQL compares the complete JSONB payload so exponent expansion does not make an identical number conflict; a different exact decimal value still conflicts, even when the difference is smaller than a binary float can represent. Exact replay preserves its original durable disposition, with no new effects. Old report session/generation or non-increasing admitted sequence is historical. Conflicts cannot mutate stored evidence. Admission verifies bound installation, known assignment, the expected keys frozen in that configuration generation, bounded timestamps, and generation before sequence comparison. Historical reports retain their original output membership. Current projection applies only to active stream incarnations with the same exact target binding; evidence for a rebound target cannot establish the replacement target's health, including before the new configuration is prepared. Controller retains a per-stream high-water mark independently of history pruning.

Emitted result maps must not contain `environment` or `environment_label`, including null values. An otherwise valid report with such an override receives `disposition: "rejected"`, `reason: "unsupported_result_environment"` and a human-readable `error`; the complete report is rejected without updating sibling results, sequence authority, incidents or evidence. Other valid reports in the same envelope remain independently admissible. Clients must tolerate optional rejection `reason`/`error` fields and must not treat a rejected report as measured recovery.

For upgrade compatibility, an exact JSONB-identical report already committed by an older controller retains its duplicate receipt when replayed by its owning installation, even if it contains these formerly ignored fields. A changed payload under that stored ID conflicts; a new ID still rejects. This exception returns existing immutable history only and cannot admit a new measurement or environment scope.

Retired assignment evidence is historical with `reason: "check_retired"`; it cannot update current health, reopen incidents or create notification work. Exact retries retain their original committed disposition. Multi-assignment transactions lock valid check identities in a deterministic order before applying reports in their original batch order.

## Operator inspection

`GET /api/v1/overview` returns bounded aggregate counts independent of visible pages. `/api/v1/checks` pages result streams, `/api/v1/checks/:id` inspects one stream, `/api/v1/configuration` pages scheduled checks, and `/api/v1/runners` lists registered runners. Page size defaults to 50 and is capped at 100; search, runner, environment, membership, health and freshness filters are supported where applicable. Result-inventory UI health filters use `OK`, `WARN`, `CRIT` and `not_measured`; freshness uses `fresh`, `stale`, `unavailable`, `awaiting` and `gaps`. Reported UNKNOWN evidence remains distinct from confirmed measured health. Selected inspection exposes the original immutable report values; JSON number spelling and object-key order can change through storage. `GET /api/v1/snapshot` remains a bounded compatibility inspection view; LiveView uses paged contexts. Current state identifies the last execution separately from `confirmed_observation_id`, `confirmed_generation`, `confirmed_session_id` and `confirmed_evaluated_at`, which identify the evidence behind retained health. `GET /api/v1/incidents/:id` loads bounded evidence, occurrences, attempts and controls for that selected incident, with totals and omission counts independent of global lists. The controller starts empty. Accepted source inventory creates UUID scheduled checks; the demo uses that same path. There is no setup/seeding API. `PUT /api/v1/assignments/:id` submits `{revision, params}` and returns 409 for stale saves or 422 for invalid complete typed parameters. Acknowledgements and maintenance use the fixed local operator, preserve measured health and never pause execution. Their reviewed APIs support indefinite/until-recovery acknowledgement, longer explicit lifetimes and scheduled maintenance windows; see [acknowledgements](../../docs/ACKNOWLEDGEMENTS.md) and [maintenance](../../docs/MAINTENANCE.md) for current request shapes, revisions and scope. Acknowledgement requests require reviewed mode and both revisions. Maintenance uses seed/preview/apply/cancel; the assignment-duration route is absent.

### Reviewed bulk configuration

Configuration inspection also accepts `configuration_stage=saved|prepared|active|measured`. This selects the highest achieved stage for the currently desired version, excludes retired checks and does not imply present evidence freshness. Rows include `configuration_stage`; `configuration_summary` includes the selected stage, the count before that stage filter within the other filters, and installation-wide active stage counts. Omitted or invalid stages select all stages. The same filter can assemble a bulk selection; applying a save still uses the frozen reviewed IDs.

Bulk editing requires explicit source opt-in through `parameter_contract`, a stable 1–128 character ASCII identifier using letters, digits, `_`, `.`, `:`, `/`, `@` or `-`. It is valid only with a nonempty, complete UI-delegated parameter schema. Compatibility requires the same `(source_id, parameter_contract)` and the exact normalized schema, including units, bounds, choices, comparisons and preserved metadata; matching field names or shapes alone do not establish shared meaning. Normalization supplies the ordinary omitted defaults (an empty comparison list and a 2048-byte string maximum) and canonicalizes integral JSON numbers by their exact decimal value, preserving schema identity across JSONB storage. The controller exposes a compact `parameter_schema_fingerprint` for selection. Checks without opt-in retain single-check editing, and omit `parameter_contract` from control and frozen configuration definitions for backward compatibility.

The following JSON endpoints share the `/api/v1/configuration/bulk` prefix and use `POST`. Prepare, preview and status return at most 25 display rows per page. Selection is bounded to 512 unique `{id, revision}` records and retains the exact revisions shown to the operator. Requests retain the ordinary 256 KiB limit.

| Route | Body | Result |
| --- | --- | --- |
| `/select` | `{filters}` | Exact selection, eligible count and excluded count; more than 512 eligible matches requires narrower filters. Ordinary inventory filters can be combined with `source_id`, `parameter_contract` and `schema_fingerprint`. Exclusions are counted against the inventory filters before compatibility filtering. |
| `/prepare` | `{selection, page?}` | Validated shared schema, common parameters, explicitly mixed fields, target rows and `prepare_token`; no writes. |
| `/preview` | `{prepare_token, params, page?}` | Complete proposed values, current/proposed rows, changed/no-op counts, affected result count and `review_token`; no writes. |
| `/apply` | `{review_token, params}` | One atomic save and receipts `{id, revision, target_generation, changed}`. |
| `/status` | `{receipts, page?}` | Batched per-receipt progress and counts for pending, prepared, active, measured, superseded, retired or missing checks. |

Purpose-specific signed tokens expire after 15 minutes. They bind the exact selection revisions and source, definition, contract and schema identity through compact digests; the review token additionally binds the complete proposed parameter set. A preparation token cannot authorize apply, and changed values require a new preview. Ordinary preparation, activation, heartbeat and measurement progress does not invalidate the reviewed configuration. Stale membership or configuration returns 409 with `stale_selection`; expired reviews and changed reviewed values return 409, while malformed tokens, incompatible selections and invalid values return 422. Clients preserve drafts on conflict or reconnect and explicitly review again without silently replacing old selected revisions. Paging must retain the original review token rather than silently renew its expiry.

Apply locks all affected runners in ID order before locking checks in ID order, revalidates the exact review and expiry, and enforces complete parameter and shared future control-response bounds in the same transaction. Any failure rolls back every changed check. An unchanged valid parameter set creates no generation or history row, but a stale reviewed revision still conflicts. The atomic boundary is the desired configuration save; each runner independently prepares and activates its saved generations, and each result independently produces evidence. Status tracks the receipt's target generation: a later desired generation is superseded, and Measured records an achieved fresh complete measurement milestone without claiming that the evidence remains fresh now.

Runtime packaging supplies `MONDEK_CONTROLLER_URL`, `MONDEK_STATE_DIR` to runner, `MONDEK_WEBHOOK_URL` to controller. The receiver/target local fixture listens on 8080, with `/ready`, `/data`, `/webhook`, `/records`, and `POST /mode` accepting readiness, backlog and webhook behavior; its recording state persists in its own volume.

Checks are created and withdrawn through complete source inventories. A fresh controller starts empty; the demo runner publishes ordinary Python checks with UUID assignment identities. `GET /api/v1/assignments/:id` returns its projected state, and `/inspection` adds bounded incident/control/evidence history independent of global windows. `POST /api/v1/notifications/:id/retry` takes `{reason}` and transactionally schedules a fresh attempt budget only for exhausted, still-relevant work after its previous job is terminal. Conflicts return 409; invalid typed inputs return 422. The same immutable notification ID/payload/destination remain, with an attributable control record.

Snapshot current state also includes `confirmed_params` for the configuration behind retained health. Notification inspection adds parent check/incident context, effective `gates`, `gated_until`, `next_retry_at`, `latest_attempt`, and `attempt_count`. A zero-second acknowledgement explicitly ends that incident's acknowledgement, independently of check maintenance. Ending acknowledgement and automatic invalidation by higher severity are recorded in control history. Terminal closure notifications remain eligible during acknowledgement and maintenance.

`waiting_on_gates` identifies queued notification work currently held by controls; gates alone describe eligibility of future attempts, not cancellation of an in-flight delivery or a restart of exhausted work. `next_retry_at` retains the real job schedule or gate expiry and can be in the past when eligible work is overdue. Incidents carry `closing_observation_id` independently of notifications, and selected incident inspection includes that measurement when retained. Older incidents without an exact historical link expose null rather than inferring a closing observation from nearby runs.
